# 华为C语言编程规范

基于华为DKBA 2826-2011.5《C语言编程规范》。编写或修改C代码时必须遵守以下规则。

## 规则优先级

- **规则（Rule）**：必须遵守，违反即视为代码缺陷
- **原则（Principle）**：总体指导思想  
- **建议（Suggestion）**：推荐做法，非强制

---

## 1. 头文件

- **原则1.1**：头文件应职责单一，仅包含接口声明，不包含实现
- **规则1.1**：头文件必须使用#ifndef/#define/#endif防止重复包含，禁止#pragma once
- **规则1.2**：禁止头文件循环依赖
- **规则1.3**：禁止在头文件中定义变量（全局变量定义应在.c文件中）
- **规则1.4**：头文件必须自包含，即不需要其他头文件前置即可编译
- **建议1.1**：头文件应包含所有需要的内部#include，不应依赖使用者提前包含
- **建议1.2**：系统头文件用<>，用户头文件用"
- **建议1.3**：头文件排列应有统一顺序（按功能块、文件名升序或稳定度排序）

## 2. 函数

- **原则2.1**：一个函数仅完成一件功能（单一职责原则）
- **原则2.2**：重复代码应提炼成函数（重复2次应消除，超过3次必须立刻消除）
- **规则2.1**：新增函数不超过50行（NBNC：非空非注释行）
- **规则2.2**：新增函数的代码块嵌套深度不超过4层
- **规则2.3**：可重入函数应避免使用共享变量（全局/static），若必须使用应用互斥手段保护
- **规则2.4**：参数合法性检查由调用者负责还是接口负责，应在项目组内统一规定
- **规则2.5**：函数应避免使用全局变量、静态局部变量和I/O操作
- **规则2.6**：废弃代码必须及时清除
- **规则2.7**：函数参数应使用有意义的命名
- **规则2.8**：禁止使用goto语句（例外：错误处理统一出口时允许）

## 3. 标识符命名

- **原则3.1**：命名应清晰明了，使用完整单词或大家都能理解的缩写
- **规则3.1**：变量命名使用snake_case，如int input_data;
- **规则3.2**：宏、常量命名使用全大写+下划线
- **规则3.3**：结构体、枚举、联合体命名使用PascalCase
- **规则3.4**：全局变量加g_前缀，如int g_status;
- **规则3.5**：静态变量加s_前缀
- **规则3.6**：指针变量建议加p前缀
- **规则3.7**：禁止单字符变量名（循环变量i/j/k除外），禁止拼音

## 4. 变量

- **原则4.1**：一个变量只有一个功能
- **原则4.2**：结构功能单一，不要面面俱到的数据结构
- **原则4.3**：不用或少用全局变量
- **规则4.1**：防止局部变量与全局变量同名
- **规则4.2**：通讯结构体必须注意字节序，发送前进行主机序到网络序转换
- **规则4.3**：严禁使用未初始化的变量作为右值
- **建议4.1**：全局变量应只有一个模块可修改
- **建议4.2**：使用面向接口编程，通过API访问数据
- **建议4.3**：首次使用前初始化变量，初始化位置离使用位置越近越好
- **建议4.4**：明确全局变量初始化顺序，避免跨模块依赖
- **建议4.5**：减少不必要的数据类型转换
- **建议4.6**：使用精确宽度整数类型（uint8_t、int32_t等）

## 5. 宏、常量

- **规则5.1**：宏表达式必须使用完备括号：#define RECT_AREA(a,b) ((a)*(b))
- **规则5.2**：多条语句的宏必须用do { ... } while(0)包裹
- **规则5.3**：使用宏时不允许参数发生副作用（如SQUARE(a++)）
- **规则5.4**：不允许直接使用魔鬼数字，必须定义为有意义的常量
- **建议5.1**：尽可能用函数代替宏
- **建议5.2**：常量用const代替#define

## 6. 质量保证

- **规则6.1**：打开所有编译告警，告警即错误（-Wall -Werror）
- **规则6.2**：使用静态检查工具（PC-Lint、Coverity等）
- **规则6.3**：禁止在产品代码中使用printf等调试函数
- **规则6.4**：严禁使用未经验证的输入数据
- **规则6.5**：资源申请和释放必须配对
- **规则6.6**：switch语句必须有default分支
- **建议6.1**：使用assert验证假设
- **建议6.2**：关键路径代码必须审查

## 7. 程序效率

- **原则7.1**：先保证正确性和可读性，再考虑优化
- **原则7.2**：通过数据结构和算法优化提高效率
- **建议7.1**：循环不变计算移到循环体外
- **建议7.2**：多维大数组按行连续访问x[i][j]
- **建议7.3**：创建资源池减少分配开销
- **建议7.4**：多次调用的小函数用inline

## 8. 注释

- **原则8.1**：优秀代码自我解释，注释无法补救糟糕代码
- **原则8.2**：注释清楚明了，含义准确，防止二义性
- **原则8.3**：注释解释意图(why)，不重复描述代码(what)
- **规则8.1**：修改代码时维护周边注释，删除无用注释
- **规则8.2**：文件头必须包含：版权、版本号、日期、作者、功能说明
- **规则8.3**：函数声明处注释功能/参数/返回值；定义处描述实现要点
- **规则8.4**：全局变量须有详细注释
- **规则8.5**：注释放在代码上方或右方，不可放下方

## 9. 排版与格式

- **规则9.1**：4空格缩进，禁止Tab
- **规则9.2**：if/for/while等必须用{}，即使只有一行
- **规则9.3**：每行不超过120字符；换行在低优先级操作符处
- **规则9.4**：一行只写一条语句
- **规则9.5**：if/for/do/while/case/switch/default独占一行
- **规则9.6**：双目操作符前后加空格，单目不加
- **建议9.1**：注释符与注释内容间用空格分隔
- **建议9.2**：关系紧密的代码尽可能相邻

## 10. 表达式

- **规则10.1**：表达式值在任何允许的运算次序下都应相同
- **规则10.2**：禁止表达式中嵌套赋值
- **规则10.3**：自增/自减独立为单独语句
- **建议10.1**：函数调用不作另一函数的参数
- **建议10.2**：赋值语句不写在if等条件语句中
- **建议10.3**：用括号明确表达式操作顺序
- **建议10.4**：赋值操作符不能用在产生布尔值的表达式上

## 11. 代码编译

- **规则11.1**：代码必须零告警编译通过
- **规则11.2**：禁止编译器特定扩展，使用标准C
- **规则11.3**：禁止保留被注释掉的代码

## 12. 可测性

- **原则12.1**：代码设计时考虑可测试性
- **原则12.2**：模块间低耦合，便于独立测试
- **建议12.1**：关键接口编写单元测试

## 13. 安全性

- **规则13.1**：字符串操作用安全函数（strncpy/snprintf），禁止strcpy/sprintf/gets
- **规则13.2**：字符串显式以\0结束
- **规则13.3**：整数运算须考虑溢出
- **规则13.4**：禁止外部输入作格式化字符串
- **规则13.5**：文件路径须校验，防目录穿越
- **规则13.6**：文件操作检查返回值，最小权限
- **规则13.7**：禁止system()，用execve()或CreateProcess()代替
- **规则13.8**：敏感数据用后立即清零

## 14. 单元测试

- **规则14.1**：编写代码同时编写单元测试
- **建议14.1**：单元测试关注行为而非实现细节

## 15. 可移植性

- **规则15.1**：不能重定义标准库保留标识符
- **建议15.1**：不使用硬件相关语句，用标准语句
- **建议15.2**：除非特殊需求，避免嵌入式汇编

## 嵌入式C特别注意事项

针对嵌入式开发（如本项目的STM32 + FreeRTOS环境），额外注意：

- **volatile**：硬件寄存器、中断共享变量必须声明为volatile
- **ISR**：中断服务函数应尽可能简短，不阻塞，不在ISR中调用不可重入函数
- **内存**：嵌入式系统内存有限，避免动态内存分配（malloc/free），优先使用静态分配
- **看门狗**：长时间操作需要考虑喂狗
